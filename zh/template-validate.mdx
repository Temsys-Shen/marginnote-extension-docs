模板里的错误不会报错。字段名或代号写错时，宿主静默忽略该条目，作者只能从界面上发现那颗按钮没有出现。

这一条性质决定了校验必须独立于装机进行。装到真机逐个点是最慢的一条路，而且界面上的遗漏未必能分辨出是配置写错、是宿主尚未消费，还是这条功能本来就不可见。静态校验先把可以机械判定的问题一次挡在装机之前。

前面各篇文章讲的是各处的写法，本文讲的是写完之后的确认办法。各位置可用的完整代号清单见[代号词汇表](/zh/template-vocabulary)。

# 三类静默忽略的错误

校验器查的是三类问题。这三类在界面上留下的痕迹相同，差别只在成因与排查手段。

## 字段名不在结构里

模板由几个结构体组成：`MNImmersiveTemplate` 是顶层，`Surfaces` 对应 `surfaces`，`Roster` 对应写成 `visible` 与 `overflow` 两个数组的名册，`BottomMode` 对应 `bottom.modes` 里的每一项。字段名不在所属结构的字段集合内，宿主解码时丢弃该键。

常见成因有两个。一个是拼写错误，例如把 `dockPinned` 写成 `dockPinnd`。另一个是沿用了已退役的旧字段，例如 `bottomRead`、`bottomWrite`、`bottomRecall` 这三个键属于 `bottom.modes` 之前的写法，参见[顶部工作栏与浮窗](/zh/template-surfaces)中的旧字段一节。

## 代号不在该位置的合法词汇表内

每个名册位置都有一份封闭清单。清单之外的代号被静默忽略。

常见成因同样有两个。一个是拼写错误，例如把 `act.doc.toggle` 写成 `act.doc.toggl`。另一个是代号来自别的位置，例如把 `multi.delete` 写进 `surfaces.nav`，而该代号属于卡片多选工具栏。

## 代号存在，但放错了位置

这一类最难发现，因为该代号在另一处确实合法，写在这里同样符合代号的书写形状。宿主静默忽略之后，界面上没有任何提示。

举一个经过核对的位置关系。`act.doc.toggle` 是合法代号，能够放进 `surfaces.nav`。把同一条代号放进 `bottom.modes[].tools`，校验器会报出该代号属于 `surfaces.nav`。同理，`contents` 能够放进 `surfaces.dock`，放进 `bottom.modes[].tools` 会被忽略。

作者在编写时看到的只是一个合法的代号字符串，因此只能靠工具发现放错位置。

# 校验器

校验器是 `sdk/output/tools/addon/validate_template.py`，随仓库提供，直接用 Python 运行，不需要额外安装依赖。

## 调用方式

```bash
python3 sdk/output/tools/addon/validate_template.py 你的/template.json
```

一次可以传入多个文件。退出码是错误条数的总和，因此可以直接写进脚本判断：

```bash
python3 sdk/output/tools/addon/validate_template.py 你的/template.json || echo "模板有问题"
```

不给参数时打印一行用法并以状态码 2 退出：

```text
usage: validate_template.py <template.json> [...]
```

文件读不出来时打印 `FAIL` 行，并把这一项计入错误条数。全部通过时打印：

```text
OK   [3-full.json] 字段与 id 全部合法
```

## 输出格式

每一个问题占一行，前缀是 `FAIL`，方括号内是文件名，随后是问题描述。字段名的问题这样写：

```text
FAIL [demo.json] surfaces.dockPinnd 不是 `Surfaces` 的字段（拼错？旧 schema？）
FAIL [demo.json] bottom.modes[0].behaviour 不是 `BottomMode` 的字段（拼错？旧 schema？）
FAIL [demo.json] (root).nm 不是 `MNImmersiveTemplate` 的字段（拼错？旧 schema？）
```

顶层键的路径前缀写作 `(root)`。`Roster` 的内部键写错时，前缀会给出该名册所在的位置，例如 `surfaces.nav.visibl`。

代号的问题分成两种措辞。代号完全查不到时：

```text
FAIL [demo.json] bottom.modes[].tools 里的 `act.crp` 不是合法 id（拼错？已退役？写在这里会被静默忽略）
```

代号存在但位置不对时，消息会同时指出该代号归属的位置：

```text
FAIL [demo.json] bottom.modes[].tools 里的 `act.doc.toggle` 放错位置了 —— 它属于 surfaces.nav（写在这里会被静默忽略）
```

`settings.global` 的键必须取自能力目录，否则报出：

```text
FAIL [demo.json] settings.global 里的 `notARealCap` 不在能力目录里（预设只能拨目录里的项）
```

名册里出现非字符串条目时同样报出，消息中带上该项的实际取值。

## 放行的边界

校验器对不认识的代号一律报出，不猜测、不放行。放行等于把静默忽略原样复刻一遍，配置在宿主那里仍然会被丢弃，问题只是被推迟到装机之后。

合法性判断依据两份表。一份是从宿主源码生成的各位置词汇表，另一份是能力目录。能力目录由宿主在运行时生成，校验器读取的是同一份静态条目。

## 两类跳过的写法

笔盒中的工具按序号引用，代号以 `excerpt:`、`sketch:`、`undo:` 开头。序号对应的是笔盒里的实际排布，无法在静态词汇表中列出，因此校验器跳过这三类代号。

插件贡献的芯片写作 `addon.<插件id>.<名字>`，其中的插件 id 由插件动态拼出，同样无法穷举。校验器只检查形状，正则表达式如下：

```text
^addon\.[A-Za-z0-9_.-]+\.[A-Za-z0-9_]+$
```

形状不合的报出为：

```text
FAIL [demo.json] surfaces.nav 里的 `addon..bad` 形状不对，插件 chip 应为 addon.<插件id>.<名字>
```

## 覆盖范围

校验器检查的名册位置是 `surfaces.nav`、`surfaces.dock`、`surfaces.multiSelect`、`surfaces.bottomRead`、`bottom.modes[].tools` 与 `bottom.modes[].overflow`。名册结构中的 `visible` 与 `overflow` 两个数组都会被检查。

`selectionMenu` 下的名册不在检查范围内。写作这一节是为了说明检查边界：校验器报绿不等于模板的全部名册都被检查过。`surfaces.mapColumn` 同理。

# 回归校验

`sdk/output/tools/addon/validate_built_templates.sh` 是配套的回归脚本。脚本在 `sdk/output/tools` 目录下查找路径中带 `build` 的 `template.json`，把这些文件一起交给校验器：

```bash
bash sdk/output/tools/addon/validate_built_templates.sh
```

找不到任何已构建模板时，脚本报出提示并以状态码 1 退出：

```text
FAIL 找不到任何已构建模板（回归样本没了，这门就是空转）
```

这道门守的不是模板。这些模板是宿主已知能接受的，模板本身没有错。这道门守的是词汇表没有遗漏，也就是校验器生成的各位置清单与宿主源码保持同步。

这一点决定了校验器在正常输入上乱报的后果比没有校验器更糟。词汇表一旦漏了合法代号，模板作者会照着误报去改一个本来正确的配置。因此修改校验器、调整词汇表之后，必须跑一遍这个脚本。

# 两道门

宿主解码往返验证与校验器互补，各自能发现的问题不同，两道门缺一不可。

宿主解码往返验证由 `sdk/output/tools/addon/decode_gate.sh` 完成：

```bash
bash sdk/output/tools/addon/decode_gate.sh 你的/template.json
```

这道门把宿主 `MNImmersiveTemplate.swift` 的值类型部分原样取出编译，用宿主那套 `Codable` 解码一份模板，再把解码结果重新编码，与原始 JSON 比对顶层键的差集。宿主解码时会静默忽略未知键，因此拼错的顶层键在解码时不会报错，往返一次才看得见。消息形如：

```text
FAIL 你的/template.json: 这些顶层键被宿主静默丢弃 → nm
```

这道门需要 macOS 上的 `swiftc`，编译一次需要十几秒，产物会缓存。它同时查类型错误，字段值类型不对时解码直接失败。

<Warning>
  这道门从宿主主工程的 `MNImmersiveTemplate.swift` 取源码编译。仓库检出中不含该文件，取不到时脚本报 `FAIL 找不到 MNImmersiveTemplate.swift` 并以状态码 1 退出。该门需要在具备宿主源码的环境中运行；校验器不受此限制。
</Warning>

校验器查的是另一些东西：字段名之外，代号是否在合法词汇表内、代号是否放在该位置、插件芯片的形状是否合规、`settings.global` 的键是否取自能力目录。宿主解码往返验证查不出代号拼错，因为代号是一个字符串，解码能过，宿主在运行期才丢弃。

两道门各自覆盖对方查不到的部分，缺任何一道都会漏。

# 现象与成因对照

下表列出界面上的现象与可能成因，供排查时定位。

| 界面现象 | 可能成因 | 定位手段 |
| --- | --- | --- |
| 工具行少了一项 | 代号拼错，或该代号属于其他名册位置 | 校验器报出不是合法 id，或报出放错位置并指出归属 |
| 按钮出现在 `更多` 弹层，工具行上没有 | 代号合法，`bottom.modes[].tools` 不收这条 | 把该代号改写进同一模态的 `overflow` |
| 顶部导航缺少某一颗按钮 | 代号拼错，或写在了 `surfaces.nav` 之外 | 校验器检查 `surfaces.nav` |
| 常驻浮球没有出现在右缘 | 常驻球由 `dockPinned` 控制，漏写，或写进了旧字段 `dock` | 校验器检查 `Surfaces` 的字段名 |
| 卡片多选工具栏缺少操作 | 代号属于底部工具条或能力目录，写在了 `surfaces.multiSelect` | 校验器报出放错位置并列出归属 |
| `settings.global` 的预设拨过去没有变化 | 键不在能力目录内 | 校验器报出不在能力目录里 |
| 某个设置项完全不起作用 | 顶层键拼错，或沿用了旧字段，宿主解码时丢弃 | 解码门报出被静默丢弃的顶层键 |
| 插件按钮出现，点击没有响应 | 配置这一层已经通过校验，按钮的行为由插件实现，静态校验不覆盖运行时 | 需要真机验证，见下一节 |

# 实机验收

静态校验覆盖的是配置写对没有，覆盖不了装进去之后是不是预期的那一份。

`sdk/output/tools/addon/starter_install_probe.py` 是配套的只读验收脚本。脚本连接运行中的 MarginNote，读取 Bridge 返回的模板摘要，与手写的 `sdk/output/tools/starter/template/3-full.json` 逐项比对：

```bash
python3 sdk/output/tools/addon/starter_install_probe.py
```

脚本默认只读。另有几项会改动状态，需要另行确认：加 `--activate` 先切到目标模板再验收，加 `--press` 按一下胶囊按钮并检查面板里的网页，加 `--run-command` 真跑一次卡片命令。

Bridge 的地址取自发现文件，也可以用环境变量 `MN_BRIDGE_BASE` 覆盖。令牌取自 `~/.config/mn-bridge/token`，或者用环境变量 `MN_BRIDGE_TOKEN` 提供。拿不到令牌时脚本以状态码 2 退出，并提示到 MarginNote 设置中的 Lab 一栏复制一次接入命令。

脚本最后会列出两条 Bridge 摘要里看不到的内容，这两条需要目视确认。

这一步不能由静态校验替代。校验器读的是文件，Bridge 返回的是宿主实际加载的结果，两者之间隔着打包、导入与加载。装上模板包之后，界面与 Bridge 摘要一致，才算这一份模板写成了。

## 与插件写入侧的区别

模板配置这一层没有重试，也没有错误码。校验器把每一类问题一次报全，作者改完之后重跑一次即可。

插件调用宿主接口的情况不同。写入侧存在 `indeterminate` 这一档，表示调用已经进入原生层但没有拿到落库结果。该档禁止自动重试，必须先读回状态再决定下一步。完整的三态定义见 SDK 仓库 `sdk/output/doc/` 下的写入侧错误契约文档。该约定只针对插件的接口调用，模板配置用不到。
